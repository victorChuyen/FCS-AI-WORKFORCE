## Objective and scope

Remove client-side identity bypasses, preserve the existing React/Vite, Apps Script,
Google Sheets and Cloudflare architecture, and stage the change for review. No
schema, worker IDs, VWW formula, attendance rules, deployed endpoints or production
ENV values are changed. The base SHA is a repository revision, NOT a verified
Cloudflare deployed revision. This document does not supersede Master Context or
Team Governance. This is client hardening, not a completed server security fix.

## Changes in this patch

- Require real Firebase authentication. Wrong password, popup cancellation, network
  failure or missing configuration never manufacture a pilot/admin profile.
- Discard old browser-stored profiles; never restore identity from localStorage.
- Project role/tenant from SDK custom claims, never email substrings. Normalize
  TENANT_VIEWER to the existing VIEWER role. Do not invent wildcard office access.
- Registration creates identity only; it does not enroll a new user in FCS-000001.
- Wait for SDK session resolution, clear null/error state and ignore stale callbacks.
  A normal token refresh is not treated as a logout. Explicit logout clears cached
  identity and blocks local token access even when SDK sign-out fails.
- Require email verification without administrator/domain/email-pattern exemptions.
- Keep email/password login, Google login and password reset; remove one-click
  preset account login and password prefilling from the existing login screen.
- Require a consistent SDK token and membership projection before API fetch. Ignore
  body identity metadata overrides. Discard responses after user/tenant changes.
- For direct Apps Script, send idToken in HTTPS POST body. For HTTPS gateways also
  send Authorization. This requires a paired backend verifier before rollout.
- Start AppContext with no tenant and no permissions, do not query business data
  while signed out, and do not turn failed tenant switching into local success.
- Production cannot select mock mode via localStorage or the runtime toggle.
- Disable the legacy shared-password seeder without creating/updating any users.
- Exclude local Cloudflare secrets and private provisioning inputs from future Git
  tracking. This does not remove credentials from history or revoke credentials.

## Release blockers - all must be resolved before merge/cutover

1. Backend authorization: the inspected Code.gs trusts identity/email from the body,
   includes privileged/default-tenant fallbacks and can provision from request paths.
   This PR DOES NOT repair that backend. Verify the actual deployed source first;
   then verify Firebase ID token authenticity/audience/issuer/expiry and account
   status before any tenant lookup or Sheet access. Resolve active membership by
   real Firebase UID. Enforce tenant, role and office scope on every read/write/export.
   Do not initialize masters or tenant files during ordinary request handling.
2. Deployment inventory: establish the Cloudflare deployed SHA, Firebase project,
   Apps Script project/deployment/version and active Sheet mapping. Existing sources
   reference fcs-ai-workforce; the supplied GCP console URL references a different
   project, fcs-ai-workforce-508702. Do not migrate or overwrite ENV based on a name.
3. Provisioning: verify each legitimate account's real UID, claims and server-side
   membership. Missing claims now deny access. Do not fabricate UIDs, grant from
   email text, or set emailVerified=true merely to bypass onboarding.
4. Credential containment: rotate exposed pilot account passwords individually and
   revoke their refresh tokens with an authenticated Firebase administrator. This
   was NOT performed here. Removing code does not neutralize a leaked password.
5. Staging: paired frontend/backend must pass authenticated regression tests and the
   Golden Flow using a separate test dataset. No production database migration is
   implied. Require technical review and business acceptance before production.

## Required server/staging acceptance tests - NOT RUN

| Scenario | Required result |
| --- | --- |
| Absent, malformed, expired or revoked token | Denied before any Sheet access or provisioning |
| User absent/inactive in membership registry | Denied; no default pilot tenant or role |
| Tenant A token with tenant B URL/body/worker ID | No B data read, update or export |
| Forged email, role, staffId in body | No change to verified identity/authority |
| Insufficient role or office scope | Each protected action is denied |
| Valid user and permitted office | Existing recruitment/attendance workflow works |
| Logout or account/tenant switch during a request | No stale private response displayed |
| Invalid or ambiguous attendance, repeated import | Visible exception; no silent duplicate result |
| Backend failure | Error state, not fake successful zero result or mock data |
| Mobile login/email verification | Vietnamese labels, keyboard and cancellation work |

Where a gateway returns HTTP 401/403, test the real HTTP status. Direct Apps Script
ContentService does not expose a general HTTP-status setter; test the explicit JSON
error envelope too. HTTP 200 or a hardcoded tenantIsolation flag is not proof of
successful authorization. Client tests do not replace any of these server tests.
